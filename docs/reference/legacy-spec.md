## 1.2. Бизнес-контекст

Yauza Media обслуживает крупные мероприятия (форумы, конференции, корпоративные события), на которых работают одновременно десятки фотографов. Их фотографии должны:

1. **Оперативно** (в течение минут после съёмки) попадать к редакторам-«бильдам» для отбора и обработки;
2. После обработки публиковаться в **публичный фотобанк** на yauza-media.ru, откуда их забирают пресс-службы, СМИ и партнёры;
3. Часть фотографий — отправляться на **согласование заказчику** перед публикацией.

Текущий процесс работает «по старинке»: фотографы льют по FTP в общую папку, бильды вручную скачивают через FileZilla, обрабатывают в Photoshop/Lightroom, выкладывают на сайт. Это медленно, ошибкоёмко и плохо масштабируется.

**Ориентир по функциональности** — публичный фотобанк photo.roscongress.ru. Мы повторяем удобные пользовательские сценарии (поиск, фильтры, навигация по мероприятиям/датам/разделам/сессиям) и идём дальше — добавляем закрытый конвейер «Фотофабрика» для редакционной работы.

## 1.3. Цели проекта

**Главные цели:**

1. **Автоматизировать конвейер** «камера → сайт» так, чтобы бильд тратил минимум ручных действий на каждой пачке фотографий.
2. **Дать фотографу мобильный интерфейс**, в котором он видит, что залилось, и одним кликом отправляет нужной сессии.
3. **Дать бильду веб-редактор**, в котором можно отобрать и опубликовать фотографии без скачивания на свой компьютер.
4. **Сохранить совместимость со старым процессом** — бильды, которые привыкли работать локально, должны иметь возможность скачивать архивы и работать как раньше.
5. **Запустить современный фотобанк yauzamedia.ru** на поддерживаемом стеке.

**Не-цели текущего этапа:** замена камер, нативное мобильное приложение (используем PWA), автоматизация отбора/обработки (включая ИИ-подсказки — позже).

## 1.5. Принципы проектирования

1. Простота для фотографа.
2. Совместимость со старым процессом.
3. Многоканальные уведомления.
4. Чистая структура данных — одна таблица на сущность.
5. Pluggable-компоненты.
6. Безопасность по умолчанию.
7. Документ — источник истины.
8. Визуальная преемственность с yauzamedia.ru.

## 1.6. Ограничения и допущения

**Камеры и FTP:**
- Camera (Canon, Nikon, Sony) — только **plain FTP**, без TLS.
- Камеры не дают сигнала «пачка закончилась» — конец определяется тишиной.
- Возможны повторные передачи того же файла при разрыве связи.
- Порядок прихода файлов не гарантирован.

**Сеть:** FTP и веб доступны извне. Фотофабрика и фотобанк — потенциально разные машины через HTTP API.

**Инфраструктура:** домены подняты, шаблоны фотобанка уже развёрнуты. Возможны публичные и закрытые разделы (токен).

**Известные риски:**
- Любой фотограф с FTP-доступом может залить в чужую папку. Полностью защититься нельзя из-за общего FTP-логина. Фиксируется в логах, на FTP запрещено удаление и переименование.
- При большом объёме одновременных заливок возможна задержка обработки пачек.

## 2. Роли и сценарии использования

### 2.1. Роли

| Роль | Аккаунт | Доступ | Что делает |
|---|---|---|---|
| **Супербильд** | Да | Логин/пароль + 2FA | Управляет мероприятиями, фотографами, бильдами, FTP-доступами. |
| **Бильд** | Да | Логин/пароль | Работает с пачками: отбирает, обрабатывает, публикует. |
| **Фотограф** | Нет | Ссылка-токен | Льёт по FTP, привязывает пачки к сессиям, видит архив. |
| **Заказчик** | Нет | Ссылка-токен | Лайкает отобранные фото. |
| **Внешний пользователь фотобанка** | Опц. | Открытые страницы | Ищет и скачивает опубликованные. |

### 2.2. Супербильд

Главный координатор. Один-два человека. Управляет всем: создаёт мероприятия, разделы, сессии, фотографов, бильдов, FTP-аккаунты. Видит общий дашборд и «карту мероприятия» с цветовыми статусами сессий.

### 2.3. Бильд

Редактор. Видит очередь пачек, открывает в веб-редакторе, отмечает «отобрано/отбраковано/требует обработки», скачивает оригиналы, загружает обработанные версии, отправляет на согласование, публикует. Совместимость со старым: скачать ZIP → локально → загрузить обратно.

### 2.4. Фотограф

Без аккаунта. Идентификация: имя FTP-папки + телефон. По уведомлению открывает страницу пачки, выбирает сессию, отправляет бильду. Видит свой архив за мероприятие.

### 2.5. Заказчик

По ссылке-токену. Лайкает фото (= одобрено). Не лайкнутые к закрытию согласования = отклонены.

### 2.6. User stories (сжатый список)

- **US-01.** Фотограф залил → пачка зафиксирована тишиной → уведомление → выбор сессии → бильд уведомлён.
- **US-02.** Бильд отобрал → обработал → опубликовал. Статус в архиве фотографа меняется автоматически (без отдельного уведомления).
- **US-03.** Бильд → заказчик по токену → лайки = одобрено.
- **US-04.** Без сессии → псевдо-сессия «Без названия» → супербильд разруливает.
- **US-05.** Пачка зависла → эскалация по каналам → супербильду.
- **US-06.** «Старая школа»: скачать ZIP → локально → загрузить готовое → опубликовать.
- **US-07.** Параллельные мероприятия → переключатель сверху страницы пачки.
- **US-08.** Битые файлы → пачка фиксируется без них → фотограф перезаливает битые **следующей** пачкой. Дозаливка в зафиксированную пачку не предусмотрена.

## 3. Архитектура (высокоуровневая)

### 3.1. Принципы

1. Разделение контуров: Фотофабрика и Фотобанк — два отдельных приложения, связь по HTTP API.
2. FTP — изолированная зона. Мост между FTP и ядром — отдельный сервис-наблюдатель (watcher).
3. Бизнес-логика — в одном Core API.
4. Pluggable-уведомления.
5. Хранилище — абстракция (FS на старте → S3 позже).
6. Стейтлесс веб-приложение.
7. Очереди для асинхронной работы.
8. Все лимиты и пороги — в конфиге.

**Стартовые параметры:**

| Параметр | Назначение | Старт |
|---|---|---|
| `batch.silence_seconds` | Тишина = конец пачки | 60 |
| `batch.max_photos` | Максимум фото в пачке | 300 |
| `batch.max_size_mb` | Максимум объёма | 500 |
| `batch.timeout_minutes` | Пачка зависла | 15 |
| `incoming.file_ttl_hours` | TTL в incoming | 24 |
| `originals.retention_days` | После закрытия мероприятия | 90 |
| `notify.escalation_minutes` | До следующего канала | 10 |
| `ftp.max_concurrent_uploads_per_user` | Лимит коннектов | 5 |
| `preview.sizes` | small/medium/large | 320/1024/2048 |

При превышении `max_photos`/`max_size_mb` — принудительная фиксация пачки.

### 3.2. Компоненты

```
Камеры → [1] FTP (vsftpd, chroot, upload-only)
          → [2] Watcher (детект пачек, валидация, перенос)
          → [3] Очередь (Redis/RQ или Celery) ↔ [4] Workers
          → [5] Core API (FastAPI)
              ├ [6] PostgreSQL
              ├ [7] Storage (FS → S3)
              └ [8] Notifiers (MAX, Telegram, SMS, Email, WebPush)
          → [9] Веб-фронтенды (SPA: /admin, /editor, /p/<token>, /c/<token>)
          → [10] Фотобанк yauzamedia.ru (отдельное приложение)
```

### 3.3. Описание (кратко)

- **[1] FTP** — vsftpd/pure-ftpd, chroot per photographer, upload-only.
- **[2] Watcher** — Python-демон, inotify, фиксация пачек, валидация, перенос в originals.
- **[3] Очередь** — Redis + RQ (просто) или Celery (мощно).
- **[4] Workers** — фоновые задачи: превью, уведомления, публикация.
- **[5] Core API** — FastAPI, REST + WebSocket для realtime.
- **[6] PostgreSQL** — JSONB для EXIF/метаданных.
- **[7] Storage** — FS на старте, S3 позже.
- **[8] Notifiers** — общий интерфейс `Notifier.send(...)`. Маршрутизация по ролям.
- **[9] Web** — единое SPA с несколькими кабинетами.
- **[10] Фотобанк** — отдельное приложение с собственной БД и хранилищем.

### 3.4. Потоки данных

- **A:** Камера → FTP → incoming/ → Watcher → originals/ → Batch в БД → превью → уведомление фотографу → выбор сессии → уведомление бильду.
- **B:** Бильд → published → очередь → POST в фотобанк (метаданные + файлы).
- **C:** Бильд → согласование → токен → заказчик → лайки → обновление статусов.

### 3.5. Хранение

| Данные | Где |
|---|---|
| Файлы фото | Storage |
| Метаданные | PostgreSQL |
| Юзеры (бильд/супербильд) | PostgreSQL |
| Токены | PostgreSQL |
| Очередь | Redis |
| Логи | Файлы + опц. централизованный сбор |
| Опубликованные фото | Фотобанк: своя БД + хранилище (копия) |

**Важно:** опубликованные фото **дублируются** в фотобанк (фотобанк работает даже если фотофабрика упала; разные машины; защита от удаления).

## 4. Конвейер обработки пачек

### 4.1. Жизненный цикл

```
RECEIVING → VALIDATING → FIXED → ASSIGNED → IN_EDITING → IN_REVIEW → PUBLISHED
параллельно: STALE, REJECTED, FAILED, SUSPICIOUS
```

### 4.2. Детектирование пачки

Псевдокод:

```python
def watcher_loop():
    for photographer_folder in incoming/*:
        files = list_files(folder)
        if not files: continue
        last_modified = max(f.mtime for f in files)
        now = time.now()
        silent_long_enough = (now - last_modified) > config.batch.silence_seconds
        too_many = len(files) >= config.batch.max_photos
        too_big = sum(f.size for f in files) >= config.batch.max_size_mb * MB
        if silent_long_enough or too_many or too_big:
            fix_batch(photographer_folder, files)
```

**Шаги fix_batch:** блокировка папки → снапшот → снять блокировку → валидация → создать Batch (VALIDATING) → перенос валидных в originals → битые → quarantine + Batch.invalid_files → Batch → FIXED → задачи в очередь (превью, уведомление).

**Edge case:** файл прилетел в момент фиксации — попадает в новую пачку (таймер тишины с нуля). Это норма.

### 4.3. Валидация файла

| Проверка | Если не прошёл |
|---|---|
| размер > 0 и < max_size_mb | quarantine |
| MIME = image/jpeg по содержимому | quarantine |
| JPEG-целостность (Pillow) | quarantine |
| мин. размеры (ширина/высота > 800) | quarantine |
| EXIF читается | warning, не quarantine |
| дубликат (sha256) | оригинал остаётся, дубль помечается |

Из EXIF извлекаем и сохраняем: DateTimeOriginal, Camera, Lens, ISO/expo/aperture/focal, Orientation, GPS, полный EXIF в JSONB.

### 4.4. Уведомление фотографа

Шаблон:

```
📸 Пачка #1234 принята
✅ 47 фото OK
⚠️ 3 битых: IMG_4501.jpg, IMG_4502.jpg, IMG_4510.jpg

Выберите сессию для пачки:
https://photofabric.ru/p/<token>?batch=1234
```

### 4.5. Привязка к сессии

Фотограф видит:
- Превью пачки;
- Список битых;
- Кнопку «Скачать оригиналы себе» (ZIP всех или выбранных);
- Dropdown сессий (отсортированы: текущие → ближайшие 2 ч → прошедшие сегодня → остальные → «Без сессии» в самом верху как fallback);
- Поле комментария;
- Кнопку «Отправить бильду».

При отправке: `session_id`, `photographer_comment`, статус → ASSIGNED, перенос originals/<event>/unassigned/<batch>/ → originals/<event>/<session>/<batch>/, задача «уведомить бильда».

### 4.6. Псевдо-сессия «Без сессии»

Автоматически создаётся в каждом мероприятии. Фотограф кладёт сюда, если не нашёл подходящей сессии. Супербильд видит на дашборде, разруливает.

### 4.7. Зависшие пачки (STALE)

Cron каждую минуту → ищет FIXED старше timeout → помечает STALE → эскалация (повторное уведомление по следующему каналу + супербильду). STALE не блокирует работу, бильду пока невидима.

### 4.8. Edge-cases и защиты

- Превышение лимита → принудительная фиксация.
- Прерванная заливка → недокачанный файл → quarantine → фотограф перезальёт.
- Два фотографа на одном FTP — ответственность супербильда, защита на UI (уникальное имя папки).
- Перезалив того же файла → дубль внутри пачки (не дублируется на диске) или флаг `duplicate_of` для дубля из другой пачки. Если >80% дублей — пачка SUSPICIOUS, супербильду алерт.
- Зомби-файлы в incoming/ старше TTL → cron форсирует фиксацию.
- Watcher упал во время фиксации → восстановление при старте: незакрытые транзакции (Batch VALIDATING без файлов в originals) — завершить или откатить.
- Большой объём → один watcher на FTP-сервер (избегаем race conditions), параллелятся фоновые задачи.

### 4.9. Параллельные мероприятия

В профиле фотографа супербильд указывает мероприятия (Photographer ↔ Event). По умолчанию dropdown показывает активное. Сверху переключатель.

### 4.10. Очистка и архивация

- `incoming/`: файлы не задерживаются.
- `quarantine/`: 24 ч, потом удаляется.
- `originals/`: пока мероприятие активно + 90 дней.
- `previews/`: столько же.

## 5. Модель данных (PostgreSQL)

### 5.1. Сущности

```
User ──┬── Photographer ──── Batch ──── Photo
       ├── Bilder
       └── Superbilder
Event ── Session ── Batch
                ├── PhotoEdit
                └── PhotoPublish
Event ── Client ── ReviewLink
              └── ClientFeedback
Notification ── NotificationChannel
```

### 5.2. Пользователи

#### `users`
id (UUID PK), email (unique), phone, telegram_id, full_name, role (`photographer|bilder|superbilder|client`), password_hash (null для photographer/client), is_active, created_at, updated_at.

#### `photographers` (extension users)
user_id (PK FK), **ftp_folder_name** (unique), notification_preferences (JSONB), default_event_id.

#### `bilders` (extension users)
user_id (PK FK), current_session_id, notification_preferences.

### 5.3. Мероприятия и сессии

#### `events`
id, title, description, client_id, superbilder_id, starts_at, ends_at, status (`planning|active|archived`), storage_path, settings (JSONB), created_at.

#### `sessions`
id, event_id, title, starts_at, ends_at, location, is_unassigned (bool), default_bilder_id, metadata (JSONB).

#### `event_photographers` (M2M)
event_id, photographer_id, assigned_at. PK = (event_id, photographer_id).

#### `event_bilders` (M2M)
event_id, bilder_id.

### 5.4. Заказчики

#### `clients`
id, title, contact_name, contact_email, contact_phone.

#### `client_users`
id, client_id, email, full_name, access_token (unique).

### 5.5. Пачки и фото

#### `batches`
id, event_id (nullable), session_id (nullable), photographer_id, bilder_id (nullable), status, access_token (unique), fixed_at, assigned_at, editing_started_at, editing_finished_at, published_at, photographer_comment, invalid_files (JSONB), stats (JSONB), metadata (JSONB).

**Enum batch_status:** `validating | fixed | stale | assigned | in_editing | in_review | published | rejected | failed | suspicious`.

#### `photos`
id, batch_id, original_filename, storage_filename, original_path, preview_path, sha256 (indexed), file_size, width, height, orientation, exif (JSONB), taken_at, camera_model, status (`pending|edited|rejected|published`), is_duplicate_of (FK→photos), created_at.

#### `photo_edits`
id, photo_id, bilder_id, edit_type (`crop|rotate|caption|keywords|reject|restore`), payload (JSONB), created_at.

#### `photo_metadata`
photo_id (PK FK), title, description, keywords (text[]), copyright, caption_author, updated_at, updated_by.

### 5.6. Согласование

#### `review_sessions`
id, event_id, bilder_id, client_user_id, access_token, status (`pending|partial|completed|expired`), expires_at, created_at.

#### `review_items`
id, review_session_id, photo_id, decision (`pending|approved|rejected|revision`), client_comment, decided_at.

### 5.7. Публикации

#### `publications`
id, photo_id, channel (`ftp|email|s3|webhook|direct_download`), target_config_id, status (`pending|success|failed`), published_at, error, metadata.

#### `publication_targets`
id, client_id, title, channel, config (JSONB encrypted), is_active.

### 5.8. Уведомления

#### `notifications`
id, user_id, channel (`email|telegram|sms|webpush|phone_call`), template, payload (JSONB), status (`pending|sent|delivered|failed|acknowledged`), created_at, sent_at, acknowledged_at, related_entity_type, related_entity_id.

### 5.9. Аудит

#### `audit_log`
id (bigserial), actor_id (nullable), action, entity_type, entity_id, payload, created_at, ip.

#### `system_settings`
key (PK), value (JSONB), updated_by, updated_at.

### 5.10. Индексы

- `photos.sha256` — дедупликация
- `photos.batch_id`, `photos.taken_at`
- `batches.status`, `batches.event_id`, `batches.session_id`
- `*.access_token` — unique
- `notifications.user_id`, `notifications.created_at`
- `audit_log.entity_type`, `audit_log.entity_id`

### 5.11. Решения

- UUID везде.
- На старте — одна БД; при росте — партиционирование `photos`.
- Файлы — не в БД, только пути.
- Без soft delete; статусы — через enum.

## 6. UI/UX

### 6.1. Принципы

Скорость, горячие клавиши для бильда, адаптивность ограниченная (бильд/супербильд — десктоп; фотограф/заказчик — мобильно), тёмная тема для бильда.

### 6.2. Фотограф

**Страница пачки `/b/<token>`:**
- Сводка (47 фото, 2 битых, 312 МБ);
- Превью-сетка (4-6 колонок), lightbox;
- Битые файлы (свёрнуто);
- Форма привязки: мероприятие, сессия, комментарий;
- Кнопки: Отправить бильду, Скачать оригиналы себе, Это не моя пачка;
- Состояния после отправки.

Архив фотографа — в backlog после MVP.

### 6.3. Супербильд

- **Дашборд:** алерты, карточки мероприятий, сводка дня.
- **Экран мероприятия:** табы (Обзор, Сессии, Пачки, Фотографы, Бильды, Публикации, Согласование).
- **Экран сессии:** параметры, обложка, бильд по умолчанию, список пачек.
- **CRUD** фотографы/бильды/заказчики.
- **Настройки:** глобальные параметры, шаблоны уведомлений, точки публикации, интеграции.

### 6.4. Бильд

**Дашборд:** В работе, Назначенные мне, Свободные (самозахват), Готовые.

**Экран пачки (рабочий стол):**
- Шапка с фотографом, сессией, комментарием;
- Сетка превью с чекбоксами, lightbox;
- Действия по фото: ⭐ Назначить обложкой сессии, ✗ Исключить из публикации;
- Sticky-панель: Скачать ZIP, Отметить пачку готовой, Вернуть в свободные, Эскалировать супербильду;
- Горячие клавиши: ←/→, Space, C, X, D, ?.

**Чего нет в MVP бильда:** цветокор, кадрирование, поворот, редактирование метаданных, удаление файлов, отправка на согласование, авто-публикация.
