# Yauza Photofactory — источник истины

Документ фиксирует архитектуру и порядок работ. **Любое решение сначала здесь (или в `docs/`), потом в коде.**

## Зачем этот репозиторий

Пошаговая «Фотофабрика» для Yauza Media: FTP → пачки → уведомления → веб для бильдов → позже сессии, фотобанк, PWA.

Стек: **Python 3.11+**, **FastAPI** (HTTP API и позже веб), фоновый **batch-watcher**, **PostgreSQL**, **vsftpd** на VPS.

## Принципы (кратко)

1. Один пароль FTP на всю зону `incoming/`; фотограф = **имя подпапки** (задаётся в камере, папка создаётся при первой заливке).
2. Все настраиваемые величины — в `config.yaml` (образец: `config.example.yaml`).
3. Модули сменяемые: уведомления, экспорт на Яндекс.Диск, хранилище.
4. Совместимость со старым процессом: скачать ZIP, работать локально.
5. Документ → код → проверка на VPS.

## Термины (MVP)

| Термин | В MVP |
|--------|--------|
| **Photographer** | Имя подпапки под `incoming/` (без отдельного аккаунта в БД на старте — можно завести запись при первом файле). |
| **Batch (пачка)** | Файлы одного фотографа, между которыми не было новых файлов **60 с** (по умолчанию, настраивается). |
| **Photo** | Один JPEG в пачке. |
| **Incoming** | `incoming/<photographer>/` — сюда льёт камера; после фиксации пачки папка фотографа в incoming очищается. |
| **Originals** | `originals/<event_id>/<session_id>/<batch_id>/` — после этапа с сессиями; на MVP-0 можно `originals/default/unnamed/<batch_id>/`. |
| **Backup** | Копия каждого файла при приёме (до или при фиксации пачки — см. этап 2). |

## Структура каталогов на сервере (целевая)


## FTP: одна учётка, много фотографов

- **Один** системный/FTP-пользователь (например `upload`) с паролем, известным всем фотографам на мероприятие.
- **Chroot** в `/srv/yauza/incoming` (или аналог).
- **Upload-only**: без удаления/переименования с камеры.
- Подпапка `<photographer>` = имя, **настроенное в фотоаппарате**; сервер **не создаёт** список фотографов заранее — только принимает файлы.
- Watcher при первом файле в новой подпапке может создать запись `photographer` в БД (этап 3).

## Batch watcher (логика)

1. Следит за `incoming/*/*.jpg` (и регистр .JPG).
2. При новом файле — сброс таймера тишины для этой подпапки.
3. Если **N секунд** (config: `batch.silence_seconds`, default **60**) нет новых файлов — **фиксация пачки**:
   - дедупликация (размер + имя или хеш — уточнить в модуле 2);
   - копия в `backup/`;
   - перенос в `originals/...`;
   - запись в БД;
   - постановка задач: Telegram, Яндекс.Диск.
4. Очистка `incoming/<photographer>/` после успешной фиксации.

## FastAPI

Достаточно для REST, авторизации бильдов, отдачи списков и ZIP. Тяжёлую работу (watch, очереди) — **отдельные процессы**, не внутри воркера uvicorn.

## Конфигурация

Файл `config.yaml` (не в git). Все переменные дублируются в `config.example.yaml` с комментариями.

## Безопасность (минимум)

- Секреты только в `config.yaml` / env на сервере.
- FTP без TLS — ограничение камер; компенсируем firewall, сильный пароль, по возможности allowlist IP на мероприятии.
- Веб и API — HTTPS, JWT/сессии для бильдов (этап 4).

## Связь с Cursor
